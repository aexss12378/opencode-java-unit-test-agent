# Spring Boot Java 單元測試

## 核心目標

產生以可信規格為依據，且能偵測合理錯誤實作的單元測試。不得以測試數量或測試涵蓋率取代品質判斷。

## 第一輪：選擇受測類別

第一輪只能分析與詢問範圍，禁止撰寫測試。依序完成以下閘門，未全部完成時只能繼續分析，不得詢問使用者是否確認：

1. 讀取 `pom.xml` 與既有測試確認測試框架和專案慣例。
2. 在閱讀正式原始碼的方法實作前，先搜尋並讀取所有可能的規格來源：使用者需求、`README*`、`docs/**`、`src/main/resources/**` 的設定檔。逐檔列出哪些文件明示為正式依據；找不到時也要明說，不得漏掉已找到的設定檔。
3. 盤點 `src/main/java` 的所有 Java 原始檔與頂層型別。每個介面、record、enum、例外、設定類別及一般類別都各占一列，即使結論相同也不得合併。大型專案應先批次搜尋型別宣告、註記與公開方法，再針對有行為的類別讀取完整內容，不要因檔案多而省略整個套件。
4. 正式原始碼只用於盤點類別，以及理解公開契約、依賴與程式流程。方法實作行號本身不是預期結果的規格證據；不得先從實作推導預期結果，再尋找證據支持。
5. 逐一以完整類別名稱列出每個頂層 Java 型別，標為「建議測試」或「排除」並說明原因。整個專案的需求包含所有套件；不得以「使用者未明確要求」排除子套件，也不得用套件名稱、「所有 records/enums/interfaces」或「其他類別」概括多個型別。
6. 每個建議類別都必須列出可觀察行為、可信證據的檔案與規則位置，以及測試能辨識的合理錯誤；缺少任一項就排除並註明「缺少可信規格證據」。`實作內容`、方法本體或目前回傳值不得寫成證據。實作與已宣告為權威的規格不符時，以規格設計測試並回報差異，不得詢問是否略過案例或改用現況實作；只有可信規格彼此衝突時才請使用者裁決。
7. 排除沒有自身行為的介面、單純資料載體、列舉、啟動與框架設定類別，但仍須逐一列名。Controller、Controller Advice 或轉換器只有在完全原樣轉呼叫時才能排除；若包含分支、狀態碼、欄位轉換、錯誤碼或例外轉換，應建議直接建立該類別做單元測試。不要改成建議整合測試。

第一輪回覆必須依序包含：

- 已讀取的正式規格來源。
- 「完整類別名稱 | 建議測試或排除 | 原因」清單，每個頂層 Java 型別恰好一列。
- 「建議類別 | 可觀察行為 | 證據位置 | 合理錯誤」清單。
- `已發現的頂層 Java 型別總數 = 已分類列數 = 建議列數 + 排除列數` 的核對結果；三者不相等或回覆中出現不同總數時，不得詢問確認。

全部核對完成後，才詢問使用者是否確認建議範圍。取得確認後才進入測試案例設計。

## 設計測試案例

- 撰寫前必須完整建立「規格行為 | 證據位置 | 案例與必要測資 | 合理錯誤 | 會改變的核心斷言」對照；每個列入範圍的行為都必須有案例，否則記錄不測理由。未完成不得撰寫測試，也不得添加沒有對應規格行為或可信證據的案例。
- 驗證公開且可觀察的行為，不測試私有方法或框架內部細節。
- 對數值上下限與門檻，使用剛低於、等於、剛高於的值；只有不能辨識另一種合理錯誤時才能省略其中一點。「必須為正」要分別保護零與負數，「允許零但拒絕負數」也要同時保護兩者。
- 對 `null`、空白、前綴、包含、大小寫與精確匹配等容易混淆的條件，使用能只改變該語意的最小反例，不得用其中一種代表另一種。
- 規格要求取位或固定小數位數時，測資在未套用該規則時必須產生不同結果，且斷言不得正規化或忽略這個差異。
- 驗證可設定值時，至少使用一組不同於專案預設值，且能讓硬編碼預設值產生不同結果的測資。
- 逐列做反證：把列出的合理錯誤代入後，至少一個核心斷言的實際值必須改變；否則調整測資或刪除案例，不得保留未通過反證的對照列。
- 不要呼叫受測程式或重寫相同演算法來計算預期值。
- 逐案比較案例能抓到的錯誤；若另一案例已能抓到相同錯誤，且本案例不保護另一個邊界或規則，即使名稱或數字不同也刪除。只新增能補足行為缺口的案例。
- 不得自行修改或刪除既有案例；若既有測試疑似錯誤或妨礙補強，先說明原因並請使用者確認。

## 撰寫測試

- 沿用專案既有的測試相依套件與風格；不要為撰寫測試修改 `pom.xml`。
- 預設以 `new` 建立受測類別，並注入必要依賴。
- 只對真正的協作者使用 Mockito；簡單 fake 較清楚時，優先使用 fake。
- 規格涵蓋傳給協作者的參數時，假物件必須依相關參數回傳不同結果或記錄參數；固定回傳值不能證明參數傳遞正確。
- 測試 Controller 時，直接建立 Controller 並隔離其 Service 等協作者。
- 不啟動 Spring，不使用網路、資料庫或檔案系統；時間與隨機行為必須透過可注入的固定來源控制。
- 不 mock 受測類別本身，也不要為了提高測試涵蓋率而過度 mock。
- 每個測試方法只驗證一項明確行為，採 Arrange-Act-Assert 結構。
- 使用專案既有的 JUnit 註記與斷言 API；AssertJ 已存在時可用於提高斷言可讀性。
- 斷言必須驗證規格要求的具體結果；能驗證值、狀態或例外類型時，不得只檢查非空、未拋例外或呼叫成功。
- 以情境與結果命名，例如 `shouldRejectOrderWhenQuantityIsZero`。
- 只在同一規則需測多組輸入時使用參數化測試。
- 例外測試使用 `assertThrows`；它已驗證例外型別，不要再次斷言相同型別。只有規格明確要求時才驗證例外訊息。
- Mockito 的 `verify` 僅用於協作者互動本身是規格的一部分。

## 完成前檢查

1. 每個正式原始碼頂層 Java 型別都各自分類且數量核對相等；建議類別與預期值有可追溯的具體規格位置，排除類別有明確理由。
2. 每個測試可獨立、可重複執行，且不依賴執行順序或環境狀態。
3. 每個案例的測資都能驗出對照表中的至少一種合理錯誤，且有核心斷言會改變。
4. 每個門檻的包含或排除語意都由端點與必要相鄰類別保護。
5. 沒有停用測試、無效斷言、重複案例或無證據的額外案例。
