# Spring Boot Java 單元測試

## 核心目標

產生以可信規格為依據，且能偵測合理錯誤實作的單元測試。不得以測試數量或測試涵蓋率取代品質判斷。

## 選擇工作入口

- 使用者要求處理整個專案時，先執行「專案範圍盤點」。取得使用者確認前不得撰寫測試。
- 使用者已指定單一類別，或上游流程已確認一個受測類別時，直接執行「單一類別分析」。不得重做整個專案盤點。
- 專案範圍確認後，每次只處理一個受測類別及一個 `Test.java` 候選檔。

## 專案範圍盤點

依序完成以下閘門：

1. 讀取 `pom.xml` 與既有測試，確認 JUnit 版本、測試註記、斷言 API、套件及命名慣例。
2. 在閱讀方法實作前，先搜尋並讀取使用者需求、`README*`、`docs/**` 與 `src/main/resources/**`。逐檔說明哪些內容明示為正式規格；找不到時也要明說。
3. 盤點 `src/main/java` 的所有 Java 原始檔與頂層型別。每個介面、record、enum、例外、設定類別及一般類別各占一列；不得以套件或型別種類概括。
4. 正式原始碼只用於確認公開契約、依賴與流程，不得從方法實作反推預期結果，再回頭尋找支持證據。
5. 逐一以完整類別名稱標為「建議測試」或「排除」，並說明原因。不得因子套件未被使用者點名而略過。
6. 每個建議類別都列出可觀察行為、規格檔案與規則位置，以及測試可辨識的合理錯誤。缺少任何一項時排除，原因寫明「缺少可信規格證據」。
7. 排除沒有自身行為的介面、單純資料載體、列舉、啟動類別與框架設定類別，但仍須逐一列名。Controller、Controller Advice 或 Mapper 只有在完全原樣轉呼叫時才能排除；若包含分支、狀態碼、欄位或例外轉換，應建議直接建立該類別做單元測試。

第一輪回覆依序包含：

1. 已讀取的正式規格來源。
2. 「完整類別名稱｜建議測試或排除｜原因」清單，每個頂層型別恰好一列。
3. 「建議類別｜可觀察行為｜證據位置｜合理錯誤」清單。
4. `已發現的頂層 Java 型別總數 = 已分類列數 = 建議列數 + 排除列數` 的核對結果。

數量不相等時先修正盤點。全部核對完成後，才詢問使用者是否確認建議範圍。

## 單一類別分析

1. 讀取目標原始碼、`pom.xml`、對應既有測試及使用者指定的規格。只有缺少必要資訊時，才讀取 README、Javadoc、呼叫端或直接依賴的型別；取得足夠資訊後停止搜尋。
2. 不得假設既有測試正確。逐一核對其斷言是否有可信規格依據，並避免重複相同情境與結果。
3. 只依可信證據建立預期結果。正式原始碼可用來理解介面與流程，不得單獨證明業務結果正確。
4. 明確且可信的規格與目前實作不一致時，保留依規格設計的案例與預期結果，記錄「規格與實作衝突」，並在產生或提交候選測試前停止目前任務。不得略過該案例、修改預期結果迎合實作，或繼續提交不完整的測試。
5. 只有缺少必要規格，或可信規格彼此衝突時，才提出一個具體問題並停止。不得詢問是否繼續或要求核准測試計畫。
6. 每個可提交案例只使用以下欄位：
   - `id`：使用 `UT-001` 格式。
   - `scenario`：輸入與前置條件。
   - `expected`：規格明確要求的可觀察結果。
   - `evidence`：支持預期結果的文件位置或使用者原文。

## 設計有效案例

- 建立「規格行為｜證據位置｜案例與必要測資｜合理錯誤｜會改變的核心斷言」對照。每個列入範圍的行為都要有案例或不測理由。
- 驗證公開且可觀察的行為，不測試私有方法或框架內部細節。
- 從規格選擇必要的正常、邊界與異常情境，不為增加數量建立無規格支持的案例。
- 數值上下限與門檻使用剛低於、等於、剛高於的值；只有無法辨識另一種合理錯誤時才能省略其中一點。
- 「必須為正」分別保護零與負數；「允許零但拒絕負數」同時保護零與負數。
- 對 `null`、空白、前綴、包含、大小寫與精確匹配，使用只改變該語意的最小反例，不得互相代替。
- 測試計算、格式化、排序、映射或狀態轉換時，使用真正會觸發規則的輸入，不使用不同實作也會碰巧得到相同結果的值。
- 規格要求取位或固定小數位數時，測資在未套用該規則時必須得到不同結果，且斷言不得正規化差異。
- 驗證可設定值時，至少使用一組不同於專案預設值，且能辨識硬編碼預設值的測資。
- 將每個合理錯誤代入案例；至少一個核心斷言的實際值必須改變，否則調整測資或刪除案例。
- 不得呼叫受測程式或重寫相同演算法來計算預期值。
- 比較案例可偵測的錯誤；若另一案例已保護相同行為，且沒有新增邊界或規則，刪除重複案例。
- 不得自行修改或刪除既有案例。既有測試疑似錯誤或妨礙補強時，先說明原因並取得使用者確認。

## 撰寫 JUnit 候選測試

- 沿用專案既有的測試相依套件與風格，不修改 `pom.xml`。
- 每次只建立或更新一個 `src/test/java/**/*Test.java`，套件、路徑、檔名與類別名稱必須一致。
- 預設以 `new` 建立真實受測類別，並以建構子注入必要依賴。
- 不啟動 Spring，不使用網路、資料庫或檔案系統，也不啟動外部程序。時間與隨機行為使用可注入的固定來源。
- 測試 Controller 時直接建立 Controller，並隔離其 Service 等直接協作者。
- 每個測試方法只驗證一項明確行為，採 Arrange-Act-Assert 結構。
- 使用情境與結果命名，例如 `shouldRejectOrderWhenQuantityIsZero`。
- 只在同一規則需要多組輸入時使用參數化測試。
- 使用專案既有的 JUnit 斷言；AssertJ 已存在時可用於提高可讀性。不得使用 Java 原生 `assert`。
- 斷言具體的值、狀態或例外型別；不得只檢查非空、未拋例外或呼叫成功。
- 使用 `assertThrows` 驗證例外型別，不重複斷言相同型別。只有規格明確要求時才驗證例外訊息。
- 將案例編號放在對應方法的 `@DisplayName` 或相鄰註解中。

## 需要測試替身時使用 Mockito

### 確認使用前提

1. 只對已有 `scenario`、`expected` 與 `evidence` 的案例使用 Mockito。
2. 確認 `pom.xml` 已提供 Mockito；缺少時停止並回報，不修改 `pom.xml`。
3. 沿用既有 Mockito 初始化方式。若專案使用 JUnit Jupiter、已有 `mockito-junit-jupiter` 且沒有其他慣例，使用 `@ExtendWith(MockitoExtension.class)`，不要混用 `MockitoAnnotations.openMocks`。

### 選擇測試替身

- 保持受測類別為真實物件，只模擬目前案例必須隔離或觀察的直接協作者。
- 簡單且具決定性的真實物件或 fake 較清楚時，不使用 mock。
- 不模擬值物件、資料傳輸物件、集合或列舉。
- 優先模擬專案自行擁有的邊界介面。除非正式程式直接依賴且無法隔離，否則不直接模擬第三方型別。
- 不得因受測類別有多個依賴就全部模擬；不需要測試替身時不得加入 Mockito。

### 建立虛設行為

- 優先以建構子明確建立受測物件。只有既有測試慣例使用 `@InjectMocks` 且注入結果明確時才沿用。
- 每個案例只虛設實際會使用的呼叫；只有全部案例都需要的虛設才能放入共同設定。
- 保持嚴格虛設檢查。只在已確認無法避免的單一虛設上局部使用 `lenient()`。
- 一般回傳值使用 `when(...).thenReturn(...)` 或既有 BDD 寫法。只有 void 方法需要拋出例外或執行動作時才使用 `doThrow()`、`doAnswer()`；不得為預設無動作加入 `doNothing()`。
- 優先使用真實參數及 `equals()`。同一次呼叫使用參數匹配器時，所有參數都使用匹配器，固定值改用 `eq(...)`。
- 規格涵蓋協作者參數時，使假物件依相關參數回傳不同結果或記錄參數；固定回傳值不能證明參數傳遞正確。

### 驗證協作行為

- 將每個 `verify` 視為斷言。只有規格明確要求呼叫、禁止呼叫、次數或順序，或互動是唯一可觀察結果時才使用。
- 優先驗證回傳值、例外或可觀察狀態。不得只因某個呼叫已被虛設，就再驗證相同呼叫。
- 單次呼叫使用 `verify(mock)`，不寫多餘的 `times(1)`。
- 只有規格明確要求時才使用 `never()`、`times(n)`、`InOrder` 或 `verifyNoMoreInteractions()`。
- 簡單參數以 `equals()` 或 `eq(...)` 驗證。只有需要檢查無法從結果取得的複合參數內容時才使用 `ArgumentCaptor`，且只用於驗證。

### 限制進階模擬

- 將 Spy 與部分模擬視為舊程式碼的最後手段。虛設 Spy 時使用 `doReturn()` 或 `doThrow()`，避免在設定階段呼叫真實方法。
- 不使用 `reset()`、`RETURNS_DEEP_STUBS` 或鏈式深層虛設。
- 只有一般協作者無法隔離，且案例有充分規格依據時，才能使用靜態或建構子模擬；以 try-with-resources 限制在單一測試方法內。

## 完成前檢查

1. 專案模式下，每個正式原始碼頂層 Java 型別都已個別分類，且總數核對相等。
2. 每個建議類別與預期結果都有可追溯的規格位置；每個排除類別都有明確理由。
3. 每個案例都能偵測至少一種列出的合理錯誤，且核心斷言會改變。
4. 每個測試可獨立、可重複執行，不依賴執行順序或環境狀態。
5. 每個斷言都能在對應案例的 `expected` 與 `evidence` 找到依據。
6. 沒有停用測試、無效斷言、重複案例、多餘虛設或無證據案例。
7. Mockito 僅用於必要的直接協作者；每個互動驗證都有規格依據。
8. 候選內容只包含一個測試檔，且每個案例編號都出現在對應測試方法旁。
