# Javadoc

## 建立可信契約

1. 完整讀取目標檔案，再查閱與目標宣告直接相關的規格、README、`docs/**`、測試、呼叫端、型別與設定。
2. 依序採信使用者或正式規格、公開 API 文件、原始碼可觀察行為。測試與呼叫端只能佐證目前用法，不能單獨建立宣告的通用保證。
3. 正式規格與原始碼衝突時，不修改該宣告的 Javadoc，改為回報衝突。既有 Javadoc 與現況不符時，重新產生該宣告的完整 Javadoc。
4. 每項限制、保證、是否可為 `null`、例外與標準相容性都必須有直接證據。不得將單一實作、工廠方法或呼叫方式推廣為整個 API 的契約。

## 決定範圍與慣例

- 文件化公開與保護型別及成員、介面成員與 enum 常數。
- 檢查原本已有 Javadoc 的其他宣告是否仍正確；沒有必要時不替私人或套件可見宣告新增文件。
- 依同檔案、同套件、同模組、專案文件的順序判斷主要語言與風格。仍無明確慣例時使用英文。
- 沿用專案既有術語、句型、段落長度與連結方式，但不得保留已失真的內容。

## 撰寫內容

- 以簡潔首句說明宣告用途，再補充呼叫者需要知道的前置條件、可觀察結果與副作用；不要逐行翻譯實作。
- 程式識別字與常值使用 `{@code ...}`，可導向 API 的型別或成員使用 `{@link ...}`。
- 使用 Javadoc 支援的 HTML 段落與清單；不要使用 Markdown 反引號或項目符號。
- 為所有型別參數與方法參數補上 `@param`，非 `void` 方法補上 `@return`。
- 只記錄由規格、明確檢查或方法簽章支持的 `@throws`；有 `@Deprecated` 時補上能由證據支持的 `@deprecated`。
- 保留仍正確且有價值的人工作者資訊，不臆測缺少的歷史、理由或替代 API。

## 完成前檢查

逐項核對每個事實陳述是否能指回證據、標籤是否與最新簽章一致、語言與格式是否符合專案慣例，以及內容是否只描述該宣告能承諾的行為。
