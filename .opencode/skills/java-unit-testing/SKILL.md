# Java 單元測試

## 核心限制

- 僅處理使用者明確指定的類別、方法、模組或行為。
- 不得把正式程式的現有實作直接當成正確規格。
- 在人工核准測試意圖前，不得建立或修改任何測試檔案。
- 不得修改正式程式、`pom.xml`、建置設定、工作流程設定或既有使用者變更。
- 僅沿用專案已具備的測試框架與函式庫；不得自行加入 JUnit、Mockito、JaCoCo 或 PIT。
- 唯一允許的新版本控制差異是慣例 Maven 測試目錄中的檔案：根目錄或模組下的 `src/test/**`。
- 不得呼叫子代理。規格分析、產生、驗證與審查都由目前代理依序完成。
- 對不確定、互相衝突或缺乏來源的預期行為，必須停止並詢問使用者，不得猜測。

## 第一階段：確認範圍與信任邊界

1. 確認目標類別、方法、模組與使用者希望驗證的行為。
2. 若目標不明確，先詢問使用者；不得掃描並改寫整個專案。
3. 將 Maven 外掛、測試與建置腳本視為會執行程式碼。若專案來源不可信、會接觸機密或需要網路下載，先說明風險並取得同意。
4. 從專案根目錄執行唯讀檢查：

```bash
uv run --no-project python .opencode/skills/java-unit-testing/scripts/inspect_maven_project.py --repo . --pretty
```

5. 若檢查結果為 `blocked`，停止後續工作並逐項回報阻擋原因。
6. 靜態檢查只能證明來源 `pom.xml` 直接宣告的設定；若父專案、啟用中的設定檔或外部屬性尚未解析，必須明確標示，必要時再經使用者同意執行 Maven 的有效設定檢查。多模組專案必須確認目標模組實際具有相容測試框架，不能因其他模組有 JUnit 就判定目標模組可用。

## 第二階段：保存基準

1. 必須在任何修改前建立 Git 工作樹基準：

```bash
uv run --no-project python .opencode/skills/java-unit-testing/scripts/repo_change_guard.py snapshot --repo .
```

2. 若工作樹原本已有變更，列出檔案並詢問使用者是否繼續。不得覆寫、還原或整理這些變更。
3. 優先使用專案的 `./mvnw`；只有沒有 Maven Wrapper 時才使用系統 `mvn`。
4. 先執行最小且相關的既有測試，保存成功、失敗、跳過與錯誤數量。若既有測試已失敗，後續結果必須與此基準比較，不得聲稱所有失敗由新測試造成。
5. Maven 指令若可能下載相依套件、啟動外部服務或執行未知外掛，必須先取得使用者同意。

## 第三階段：建立測試意圖

1. 讀取 [測試意圖契約](references/test-intent-contract.md)。
2. 對每一條候選規則建立獨立測試意圖，並附上可核對的來源位置。
3. 依下列分類處理：

| 分類 | 定義 | 處理 |
|---|---|---|
| `confirmed-specification` | 有權威規格，或已由使用者明確核准 | 可建立正式單元測試 |
| `current-behavior` | 只能從目前執行結果或實作觀察到，沒有規格背書 | 只能建立明確標示的行為刻畫測試 |
| `suspected-behavior` | 看似合理但缺乏足夠來源 | 等待人工確認 |
| `conflict` | 來源彼此矛盾，或規格與現況不一致 | 只阻擋受影響的測試意圖 |

4. 來源優先順序為：使用者明確核准的需求、正式需求或 API 契約、可追溯的設計文件、既有測試、目前正式程式。既有測試和正式程式只能證明現況，不能單獨把規則提升為正式規格。
5. 向使用者列出測試意圖、分類、來源、輸入與預期觀察結果，然後停止等待核准。

## 第四階段：產生測試

1. 只實作使用者明確核准的測試意圖。
2. 沿用檢查階段偵測到的測試框架、斷言函式庫、命名與專案慣例。
3. 若專案沒有相容的測試框架，或測試需要修改 `pom.xml`，立即停止並要求使用者決定；不得自行擴大權限。
4. 將測試放在目標模組的 `src/test/**`，並鏡射正式程式的套件結構。
5. 讓每個測試只驗證一個可描述的行為，使用具體預期值與可觀察結果。
6. 僅模擬不可控制的外部依賴；不得模擬受測物件本身、純資料物件或可直接建立的值物件。
7. 隔離時間、亂數、檔案、網路、執行緒與全域狀態。不得使用 `Thread.sleep()`、不穩定排序或依賴執行順序的測試。
8. 行為刻畫測試的名稱或顯示名稱必須包含 `Characterization`，並在註解中附上對應測試意圖編號。

## 第五階段：逐層驗證

依下列順序執行，前一層失敗時先診斷，不得直接擴大範圍：

1. 測試編譯。
2. 新增或修改的單一測試方法。
3. 新增或修改的測試類別。
4. 受影響模組的既有單元測試。
5. 與執行前基準比較結果。
6. 僅在 JaCoCo 已可用時，報告目標類別的行與分支覆蓋率增量。
7. 僅在 PIT 已可用時，限定 `targetClasses` 與 `targetTests`；不得對整個舊專案直接執行完整突變測試。

不要把高覆蓋率當成通過條件。覆蓋率只能指出哪些程式被執行，測試品質仍需由斷言與突變結果判定。

## 第六階段：審查與變更稽核

1. 讀取 [測試審查清單](references/review-checklist.md) 並重新檢查實際測試檔案。
2. 對每個 PIT 存活突變分類為：斷言不足、等價突變、超出核准範圍或工具限制。不得把所有存活突變一律認定為測試錯誤。
3. 執行最終範圍稽核：

```bash
uv run --no-project python .opencode/skills/java-unit-testing/scripts/repo_change_guard.py audit --repo .
```

4. 若出現 `src/test/**` 以外的新變更、基準後的提交或基準檔案不一致，停止並回報，不得自行還原。

## 最終回報

以繁體中文提供以下內容：

1. 測試目標與核准意圖。
2. 新增或修改的測試檔案。
3. 實際執行的完整指令。
4. 執行前基準與執行後結果。
5. JaCoCo 覆蓋率增量；未執行時列出經檢查的原因。
6. PIT 結果與存活突變處置；未執行時列出經檢查的原因。
7. Git 範圍稽核結果。
8. 尚未解決的規格衝突、工具限制與下一步。

不得使用「應該成功」、「看起來沒問題」或未附實際輸出的推測性結論。
