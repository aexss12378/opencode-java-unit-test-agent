# Java 單元測試

## 不可違反的限制

- 只處理使用者明確指定的類別、方法、模組或行為；範圍不清楚時先詢問。
- 不得把正式程式的現有實作直接當成正確規格。
- 每個測試意圖都必須有來源、分類與人工核准；核准前不得建立候選測試。
- 不得修改正式程式、`pom.xml`、建置設定、工作流程設定或既有測試。
- 代理不得直接寫檔。唯一發布入口是 `submit_unit_tests`，而且第一版只允許新增 `src/test/java/**`。
- 不得呼叫子代理，不得使用 Shell、Maven 外掛或其他工具繞過寫檔限制。

## 一、確認專案與範圍

1. 確認目標類別、方法、模組及要驗證的行為。
2. 讀取目標原始碼、同模組的 `pom.xml`、既有測試、README、Javadoc、正式規格與呼叫端。
3. 使用 `git status --short` 與 `git diff` 確認使用者既有變更；不得覆寫、還原或整理它們。
4. 確認專案已有相容的測試框架；不得自行加入 JUnit、Mockito、JaCoCo 或 PIT。
5. Maven 指令可能下載相依套件或執行專案程式碼，執行前依權限提示取得使用者同意。

## 二、提出測試意圖並停止等待核准

每個獨立行為建立一筆測試意圖，至少包含：

- 編號：`UT-001` 格式。
- 目標：模組、完整類別名稱、方法或類別層級。
- 分類：`confirmed-specification`、`current-behavior`、`suspected-behavior` 或 `conflict`。
- 規則：一句可驗證的行為。
- 具體輸入與可觀察的預期結果。
- 來源：檔案與行號、文件章節、議題連結或使用者原文。
- 測試種類：`unit` 或 `characterization`。

分類規則：

- `confirmed-specification` 必須有使用者核准、正式需求、API 契約或可追溯設計文件。
- `current-behavior` 只能建立明確標示的行為刻畫測試。
- `suspected-behavior` 與 `conflict` 不得由代理自行核准。
- 既有測試和正式程式只能證明現況，不能單獨提升為正式規格。
- 一筆意圖只描述一個行為，不得使用「正常」、「合理」等無法形成斷言的預期結果。

列出完整測試意圖後停止。只有使用者明確核准編號或逐項核准，才能繼續；沉默或一般討論不算核准。

## 三、準備並提交候選測試

1. 只實作已核准意圖，沿用專案現有測試框架、命名與套件結構。
2. 每個測試只驗證一項行為，使用具體斷言，不以正式程式的同一套邏輯重算預期值。
3. 只模擬不可控制的外部依賴；不得模擬受測物件、純資料物件或可直接建立的值物件。
4. 不得使用 `Thread.sleep()`、停用測試、assumption、網路、真實資料庫、系統時間、亂數或測試順序。
5. 每個候選測試必須在註解中標示對應的已核准意圖編號。行為刻畫測試名稱必須包含 `Characterization`。
6. 不得直接寫檔。呼叫 `submit_unit_tests`，提供：
   - `approved_intent_ids`：已核准意圖編號。
   - `target_classes`：無萬用字元的完整正式類別名稱。
   - `files`：新的 `src/test/java/**` 路徑與完整 Java 原始碼。

## 四、依工具結果處理

`submit_unit_tests` 會在隔離副本依序執行既有測試基準、候選測試編譯、完整測試、Maven `verify`，並在專案已有設定時執行 JaCoCo 與限定目標的 PIT。全部完成且原專案未發生受保護變更後，才發布新測試檔。

- 只有工具回傳 `published` 才代表完成；其他狀態不得改走別的寫檔途徑。
- `candidate-tests-failed` 可能代表候選測試錯誤，或正式程式與核准規格衝突。
- 若預期值有獨立規格依據，不得為了通過而改成目前實作的結果。
- 不把高涵蓋率或高突變分數當成業務規則正確的證明。

## 五、最終回報

以繁體中文提供：

1. 測試目標與已核准意圖。
2. 工具實際發布的測試檔案。
3. 工具實際執行的完整指令與結果。
4. 執行前後測試數量。
5. JaCoCo 與 PIT 結果；未執行時說明經確認的原因。
6. `git status --short` 與 `git diff` 顯示的最終範圍。
7. 尚未解決的規格衝突與工具限制。

不得使用「應該成功」、「看起來沒問題」或其他沒有實際輸出的推測性結論。
