# Java Mockito 測試替身

## 確認使用前提

1. 只處理 Agent 已確認且具有 `scenario`、`expected`、`evidence` 的測試案例。
2. 確認 `pom.xml` 已提供 Mockito，並沿用既有版本與測試風格；缺少時停止並回報，不修改 `pom.xml`。
3. 沿用既有 Mockito 初始化方式。若專案使用 JUnit Jupiter、已有 `mockito-junit-jupiter` 且沒有其他既有慣例，使用 `@ExtendWith(MockitoExtension.class)`，不要再混用 `MockitoAnnotations.openMocks`。

## 選擇需要模擬的對象

- 保持受測類別為真實物件，只模擬為完成目前案例而必須隔離或觀察的直接協作者。
- 能以真實且具決定性的簡單物件完成測試時，直接使用真實物件；不要模擬值物件、資料傳輸物件、集合或列舉。
- 優先不要直接模擬第三方型別；若專案已有自行擁有的邊界介面，改為模擬該介面。只有正式程式直接依賴第三方型別且目前案例無法以真實物件隔離時，才能依其公開契約建立必要虛設，不驗證第三方內部行為。
- 不得因類別具有相依物件就全部模擬。沒有需要模擬的協作者時，不得加入 Mockito 程式碼。

## 建立與虛設行為

- 優先以建構子明確建立受測物件，使相依關係可見；只有既有測試慣例使用 `@InjectMocks` 且注入結果明確時才沿用。
- 每個案例只虛設實際會使用的呼叫，並盡量放在對應測試方法內；只有所有案例都需要的虛設才能放入共同設定。
- 保持 Mockito 的嚴格虛設檢查。只有已確認無法避免的單一虛設才能局部使用 `lenient()`，不得將整個測試類別設為寬鬆模式。
- 一般回傳值使用 `when(...).thenReturn(...)` 或專案既有的 BDD 寫法。只有 void 方法需要拋出例外或執行動作時才使用 `doThrow()`、`doAnswer()`；不得為預設無動作行為加入 `doNothing()`。
- 優先使用真實參數及 `equals()` 比對。使用參數匹配器時，同一次呼叫的所有參數都必須使用匹配器，固定值改用 `eq(...)`。
- 不得只因某個呼叫已被虛設，就再驗證同一呼叫是否發生。

## 驗證協作行為

- 將每個 `verify` 視為斷言；只有 `expected` 與 `evidence` 明確支持該互動時才能加入。
- 優先驗證回傳值、例外或可觀察狀態。只有對外呼叫、禁止呼叫、呼叫次數或順序本身是規格要求，或該呼叫是唯一可觀察結果時，才驗證互動。
- 單次呼叫使用 `verify(mock)`，不得寫多餘的 `times(1)`。
- 只有規格明確要求未呼叫、特定次數或順序時，才能使用 `never()`、`times(n)` 或 `InOrder`。
- 不得例行加入 `verifyNoMoreInteractions()`；只有「除此之外不得有其他互動」本身是規格要求時才能使用。
- 簡單參數直接以 `equals()` 或 `eq(...)` 驗證。只有必須檢查無法從結果取得的複合參數內容時，才使用 `ArgumentCaptor`，且只用於驗證，不用於虛設。

## 限制進階模擬

- 將 Spy 與部分模擬視為舊程式碼的最後手段。虛設 Spy 時使用 `doReturn()`、`doThrow()` 等方式，避免在設定階段呼叫真實方法。
- 不得使用 `reset()` 重複利用測試替身；每個測試建立乾淨的替身。
- 不得使用 `RETURNS_DEEP_STUBS` 或鏈式深層虛設。優先使用真實回傳物件，或為直接協作者明確建立個別替身；仍無法隔離時停止並回報。
- 只有現有介面無法以一般協作者隔離，而且案例有充分規格依據時，才能使用靜態或建構子模擬；必須以 try-with-resources 限制在單一測試方法內。

## 建立候選前自我檢查

重新讀取完整候選測試並確認：

1. 每個模擬物件都是必要的直接協作者，且受測物件本身是真實物件。
2. 每項虛設都會被目前案例使用，沒有共同設定造成的多餘虛設。
3. 每個互動驗證都能在該案例的 `expected` 與 `evidence` 找到依據。
4. 沒有多餘的 `times(1)`、`doNothing()`、`verifyNoMoreInteractions()`、`lenient()` 或 `reset()`。
5. `ArgumentCaptor`、Spy、靜態或建構子模擬只在對應限制成立時使用。
6. 所有 Mockito API 與 JUnit 整合方式都由專案既有相依套件提供。
