# 企業訂單放行規格

本文件是 `OrderPlacementService.place` 與訂單放行 API 的正式依據。實作或既有測試若與本文件衝突，以本文件為準。

## 1. 輸入驗證

1. 訂單編號、冪等鍵、顧客編號、商品編號、幣別與付款權杖不可為 `null` 或空白。
2. 訂單編號不得超過 64 個字元；冪等鍵不得超過 128 個字元。兩者建立後必須保留原值，不做大小寫或空白正規化。
3. 幣別必須是三個大寫英文字母，金額不可為 `null`；金額建立後必須保留原本數值與小數位數。
4. 數量與訂單總額必須大於零。
5. 訂單總額可等於設定的最高金額，但不得超過。
6. 幣別必須與設定值完全相同，包含大小寫。
7. 驗證失敗時拋出 `IllegalArgumentException`，且不得呼叫 DAO、風險、庫存或付款協作者。

## 2. 冪等

1. 冪等鍵採完全相同比對，區分大小寫且不做前後空白正規化。
2. 找到相同冪等鍵及完全相同的命令時，直接回傳 DAO 中的先前結果；不得再次呼叫風險、庫存、付款或儲存操作。
3. 相同冪等鍵搭配不同命令時，拋出 `IdempotencyConflictException`；不得呼叫風險、庫存或付款協作者。
4. 第一次處理產生的每一種業務結果都必須連同原始命令的指紋保存一次。
5. DAO 以冪等鍵查找資料，新增資料時不得改寫冪等鍵、指紋或業務結果欄位。

## 3. 請求指紋

1. 指紋依序涵蓋訂單編號、冪等鍵、顧客編號、商品編號、數量、金額、幣別及付款權杖，不得遺漏欄位。
2. 每個欄位使用 UTF-8 的「位元組長度、冒號、原值、分隔符號」格式串接，再產生 SHA-256 小寫十六進位字串。
3. 金額使用保留小數位數的十進位字串；因此 `100.0` 與 `100.00` 是不同命令。
4. 任一欄位內容、大小寫、前後空白或金額小數位數改變，指紋都必須改變。
5. 資料庫只保存指紋，不得保存付款權杖。
6. 範例命令 `ORD-20260804-001`、`req-001`、`CUST-001`、`SKU-BOOK`、數量 `2`、金額 `1200.00 TWD`、付款權杖 `TOKEN-OK-001` 的指紋固定為 `739474f440337ffafa048fc9b0ef9f43c8826b58f89be8e6c14559db0a3d89b4`。

## 4. 風險分流

1. 風險分數必須介於 0 到 100，包含端點；超出範圍時拋出 `IllegalStateException`。
2. 分數大於或等於拒絕門檻時回傳 `RISK_REJECTED`。
3. 分數大於或等於人工審查門檻、但低於拒絕門檻時回傳 `MANUAL_REVIEW`。
4. 只有低於人工審查門檻時才能進入庫存保留。
5. 人工審查或風險拒絕時，不得呼叫庫存或付款協作者。

## 5. 庫存、付款與補償

1. 庫存保留必須收到命令中的原始商品編號及數量。
2. 保留失敗時回傳 `OUT_OF_STOCK`，不得呼叫付款協作者。
3. 保留成功後，付款授權必須收到原始訂單編號、總額、幣別及付款權杖。
4. 付款拒絕時，必須釋放本次取得的同一筆庫存保留，然後回傳 `PAYMENT_DECLINED`。
5. 付款成功時不得釋放庫存，回傳 `ACCEPTED`，並保留庫存編號及付款授權編號。

## 6. 付款期限

付款成功的期限等於注入時鐘的當前時間加上設定的授權期限。不得讀取系統時鐘，也不得硬編碼設定檔中的預設期限。

## 7. 資料轉換

1. API Mapper 必須逐欄把請求轉為命令，並建立 `OrderId`、`IdempotencyKey` 與 `Money` 值物件；不得調整大小寫、去除空白或改變金額小數位數。
2. API Mapper 必須逐欄把業務結果轉為回應，不得遺漏狀態、訂單編號、庫存編號、授權編號或付款期限。
3. Persistence Mapper 必須把冪等鍵、指紋與完整業務結果寫入 Entity，並能還原相同業務結果。

## 8. HTTP 狀態

- `ACCEPTED`：201 Created
- `MANUAL_REVIEW`：202 Accepted
- `OUT_OF_STOCK`：409 Conflict
- `RISK_REJECTED`、`PAYMENT_DECLINED`：422 Unprocessable Entity
- 冪等鍵衝突：409 Conflict，錯誤碼為 `IDEMPOTENCY_CONFLICT`
